Living log of how HeatOps (FortyGuard Hackathon'26, deadline **2026-08-30 11:59 PM GST**) is being built. Updated after every development step so the project's history and reasoning survive even if a chat session doesn't. Reverse order is not used — read top to bottom, oldest first.

For the full feature spec and step order, see the original brief. For FortyGuard API constraints (rate limits, AOI size cap, polling backoff, etc.), see `lib/fortyguard.ts` once it exists in Step 5 — until then those constraints live only in the brief.

## Step 2 — Base map + search + view mode toggle

**Built:**
- Live MapLibre GL map in `MapCanvas.tsx`, style: OpenFreeMap "liberty" (free, no API key)
- Default center: **Phoenix, AZ** (`lib/mapConfig.ts`) — FortyGuard coverage is US-only; Phoenix chosen for the urban-heat-island story fit (user is actually based in Istanbul, so this is a deliberate override)
- `SearchBox` — queries `/api/geocode` (server-side proxy to Nominatim, with a descriptive `User-Agent` per their usage policy — calling Nominatim directly from the client risks rate-limiting/blocking), `flyTo`s the first result
- `ViewModeToggle` — "Schematic" (vector) vs "Satellite" (Esri World Imagery raster) toggle. Both layers coexist on the map; toggling just flips `visibility` via `setLayoutProperty` rather than swapping the whole style, so switching is instant with no flicker or re-fetch
- Esri World Imagery raster source capped at `maxzoom: 19` — real imagery resolution runs out around z19 in most US areas; past that Esri serves a fixed-size (~2521 byte) "map data not available" placeholder tile instead of a 404. Capping `maxzoom` makes MapLibre over-scale the last real tile instead of requesting the placeholder.
- Layout: `SearchBox` (top-left) and `ViewModeToggle` share one row via a 3-column CSS grid (`grid-cols-[auto_1fr_auto]`) so the toggle centers in the *remaining* space next to the search box — mathematically guaranteed not to overlap it at any viewport width. Native zoom control moved to bottom-right to stay clear of both.

**Notable bugs fixed:**
1. **maplibre-gl v6.4.1 never fired `style.load`** (`map.loaded()` stayed `false` forever, zero vector tile requests were ever issued despite the style/sprite/font all fetching fine). Root-caused by direct inspection of the live `Map` instance (`document.visibilityState`, `map.style.loaded()`, resource timing entries) rather than guessing. Fix: downgraded to v4.7.1, which works correctly.
2. Esri "data not available" tiles at high zoom — see above, fixed with `maxzoom: 19`. Confirmed via `curl`: tile byte size was a constant 2521 bytes at z20+ (the placeholder) vs. 13–21KB of varying size for real photo tiles at z15–19.
3. This automation/browser-testing environment defaults new tabs to `document.visibilityState: "hidden"`, which suspends `requestAnimationFrame` and therefore MapLibre's tile-loading render loop — caused a long, confusing debugging detour early in Step 2 that turned out to be an artifact of the test tooling, not the app. Worth remembering if a map ever appears to silently not render tiles again despite everything else checking out.

**Validated:** Manually in browser — default Phoenix view renders full detail (roads, labels), search "Houston, TX" flies correctly to downtown Houston, Schematic ↔ Satellite toggles instantly both directions with correct Esri attribution, zoomed deep into Satellite mode past z19 and confirmed real (over-scaled) imagery instead of the placeholder. `tsc` + `lint` clean throughout.

## Step 4 — Land-cover breakdown (FortyGuard satellite + Overpass cross-check)

**Built:**
- `lib/fortyguard.ts` (server-only, `import "server-only"`) — `runSatelliteSegmentation()`: submits to `POST /v1/satellite` (point-based: `sat.latitude`/`sat.longitude`, not a polygon), then polls `GET /v1/status/{activity_id}` with the required 3s→6s→12s backoff (holds at 12s, gives up after 10 attempts). Uses `filter_type: 3` (Single Day) so only `start_date` is needed — defaults to today's date, since there's no heatmap yet (Step 5) to match dates with.
- `lib/overpass.ts` (server-only) — queries Overpass for `building` ways and `highway` ways inside the AOI's bbox, converts OSM node/way JSON to GeoJSON manually (no relations/multipolygons — good enough for a few-block AOI), buffers roads by an estimated width per highway class, and clips everything to the exact drawn AOI polygon via `turf.intersect`. This is the "clipped to AOI" data FortyGuard's point-based endpoint can't give directly.
- `app/api/landcover/route.ts` — POST endpoint taking `{ geometry }`, validates against `MAX_AOI_AREA_SQKM`, computes the AOI centroid via Turf, and runs the FortyGuard + Overpass calls in parallel via `Promise.allSettled` (one failing doesn't take down the other).
- `store/landcoverStore.ts` (Zustand) — idle/loading/success/error state for the panel; `AnalyzePanel` resets it whenever the AOI geometry changes so stale results never show against a new/absent AOI.
- `AnalyzePanel` — "Analyze land cover" button (disabled while over the area limit or already loading; not auto-triggered on every draw, since the FortyGuard call is a paid Premium endpoint). On success renders two cards: FortyGuard's segment breakdown (dynamic class list — labels/colors assigned generically since the API doesn't document a fixed class set — plus the original satellite thumbnail and segmentation mask image, both returned as base64) and the Overpass footprint cross-check (buildings/roads/other %, building+road counts), each tagged with a `SourceBadge` ("Real (FortyGuard)" / "Real (OpenStreetMap)"). A caption clarifies FortyGuard's imagery is centered on the AOI centroid, not clipped to the drawn boundary — Overpass is the boundary-exact number.
- `.env.local` — `FORTYGUARD_API_KEY` (gitignored via existing `.env*.local` rule).

**Design decision — FortyGuard `/v1/satellite` is point-based, not polygon-based:** the project brief assumed this endpoint would take the AOI polygon and return clipped results, matching the `/v1/heatmap` pattern. Docs (fetched live from docs-api.fortyguard.com via browser, since the JS-rendered site isn't reachable by plain HTTP fetch) show it actually takes a single `sat.latitude`/`sat.longitude` and returns a fixed-size segmentation image centered on that point. Reconciled by querying at the AOI centroid and leaning on the Overpass cross-check for the boundary-exact numbers, with the UI captioning the distinction rather than presenting FortyGuard's % as if it were clipped.

**Notable bugs fixed:**
1. Overpass returned `406 Not Acceptable` on every request. Root cause: Node's `fetch` (undici) sends no `User-Agent`/`Accept` header by default, and Overpass's Apache front-end rejects such requests — same descriptive-UA requirement as Nominatim (see Step 2's `geocode` route). Fixed by adding `User-Agent: HeatOps/1.0 (FortyGuard Hackathon 2026)` and `Accept: */*` to the Overpass fetch. Confirmed via a standalone `node -e` repro before touching the route code.
2. `turf.helpers.Feature` doesn't exist as an exported type in Turf 7 (`tsc` caught this) — fixed by importing `Feature` from the `geojson` package instead, same as `Polygon` was already imported.

**Validated:** Ran the real pipeline end-to-end in a browser against the live FortyGuard API (using the user's real key) and the live Overpass API — drew a ~15 ha AOI over downtown Phoenix, clicked "Analyze land cover", confirmed both cards populate with real data: FortyGuard returned Building/Road, Route/Sidewalk, Pavement/Tree/Earth, Ground/Grass segments plus a real satellite thumbnail and segmentation mask overlay; Overpass returned 34.2% buildings / 26.0% roads / 39.7% other from 28 buildings and 25 road segments clipped to the AOI. Redrew the AOI and re-ran to confirm the Overpass fix and the stale-result reset both work. `tsc --noEmit` and `next lint` clean (only the expected `no-img-element` warnings for the two base64 thumbnails, which can't use `next/image`).

## Step 5 — Heatmap generation, Part 1 & 2 (fetch + clipped render)

Scope revised: per `project.md` (saved to repo root, not `docs/`), the build is now split into **Map View** (data acquisition + save-to-Supabase) and a separate **Operational Analyst** page (analysis + charts, reads only from Supabase — never calls FortyGuard again). This step covers only the Map View heatmap fetch + render; Supabase persistence and the 3 output photos are later steps.

**Part 1 — `lib/fortyguard.ts`: `runHeatmapGeneration()`**
- Accepts the **full AOI polygon**, wraps it in the `polygon_aoi` FeatureCollection envelope, `filter_type: 3` (Single Day), granularity passed by the caller (route calls it with `HEATMAP_GRANULARITY_M = 60`).
- `activity_id` was already read from `body.data.activity_id` (not top-level) — user flagged this as a possible bug from a newer official code sample, but the existing code already matched it; no change needed there.

**`polygon_aoi` shape ambiguity, resolved empirically:** two official FortyGuard sources disagreed — the developer docs (`docs-api.fortyguard.com`) wrap `polygon_aoi` in a GeoJSON FeatureCollection; the marketing site's code sample (`fortyguard.com/products`) sends a bare `{type: "Polygon", coordinates}`. Resolved by live-testing both shapes against the real API (with explicit user go-ahead after an earlier unplanned credit spend — see Known environment issues below): **both are accepted and produce identical results.** Kept the FeatureCollection-wrapped form since it matches the developer docs.

**Real response shape, confirmed empirically (not guessed):**
- `map_data`: GeoJSON `FeatureCollection<Polygon>`, one feature per tile, `properties: { tile_id, average_temperature, min_temperature, max_temperature }` — all lowercase, unlike the docs prose which showed capitalized field names.
- `stats_data.temperature_stats`: `{ minimum, maximum, mean, standard_deviation }` — again lowercase, contradicting the docs prose's `Minimum/Maximum/Mean/Standard_deviation` capitalization.
- `stats_data.temperature_frequency`: `{ x_axis: number[], y_axis: number[] }` (parallel arrays: temperature bin, count) — not the `Record<string, number>` initially guessed before this was confirmed.
- Types in `lib/fortyguard.ts` (`HeatmapTileProperties`, `HeatmapResult`) now match this exactly.

**Part 2 — clipped rendering**
- `lib/tempToColor.ts` — green→yellow→orange→red gradient anchored to fixed absolute thresholds (26.7°C / 29.4°C / 31.1°C / 33.3°C — landmarked on the published NIOSH/OSHA-NIOSH WBGT heat-stress flag bands, themselves aligned with ISO 7243's reference values), not the current AOI's own min/max — so tile color is comparable across different sites. Documented in-code as a visual proxy, not a certified WBGT calculation (FortyGuard's tile value is a surface/air temperature; true WBGT needs humidity/wind/radiant heat data FortyGuard doesn't return).
- `mapConfig.ts`: added `HEATMAP_GRANULARITY_M = 60`, shared between the API route (request granularity) and `MapCanvas` (GridCellLayer `cellSize`) so rendered cells match the fetched grid spacing.
- `app/api/heatmap/route.ts` — POST `{ geometry }` → validates against `MAX_AOI_AREA_SQKM`, calls `runHeatmapGeneration`, returns `{ areaSqKm, result }`.
- `store/heatmapStore.ts` — idle/loading/success/error, `AnalyzePanel` resets it on AOI change (same pattern as `landcoverStore`).
- `MapCanvas.tsx` — added a `@deck.gl/mapbox` `MapboxOverlay` control (non-interleaved) alongside the existing MapLibre map. On heatmap-data/AOI change, builds a `GeoJsonLayer` with `operation: "mask"` from the AOI polygon and a `GridCellLayer` (one cell per tile, `getPosition` from each tile polygon's Turf centroid, `getFillColor` from `tempToColor`, `extensions: [new MaskExtension()]`, `maskId` pointing at the mask layer) — cells outside the AOI boundary are clipped.
- `AnalyzePanel.tsx` — new "Surface heatmap" card with its own "Generate heatmap" button, independent of the land-cover card (both read from the same drawn AOI).

**Packages added:** `@deck.gl/core`, `@deck.gl/layers`, `@deck.gl/extensions`, `@deck.gl/mapbox` (all `9.3.10`, matched to work with the pinned `maplibre-gl@4.7.1`).

**Validated:**
- `tempToColor()` checked directly against the threshold boundaries and the real observed tile temperatures (~32.4°C → correctly lands in the orange→red band).
- Render pipeline (GridCellLayer + MaskExtension clipping) verified in-browser using the **real tile data already obtained** from the empirical `polygon_aoi` test (translated to sit under the default Phoenix map view; temperatures/geometry otherwise untouched) — `window.fetch` was temporarily monkey-patched in the browser console to serve this fixture instead of calling `/api/heatmap` for real, specifically to avoid a second unplanned credit spend. Drew a generous AOI: all 4 real tiles rendered, colored orange/red matching their real ~32.4°C values. Redrew a narrower AOI covering only the left half of the tile row: only 2 of 4 tiles remained visible, confirming `MaskExtension` clips correctly rather than just rendering everything unclipped. `tsc --noEmit` and `next lint` clean throughout.
- **Not yet tested:** an actual live "Generate heatmap" click against the real FortyGuard API — deliberately deferred pending explicit user go-ahead (see Known environment issues below), since it costs a real credit on completion.

## Step 8 — FortyGuard cached mode (credit-free dev/testing)

User asked to mirror the FortyGuard Quickstart notebook's `CACHED=True` mode: *"the Quickstart has a cached mode you can use to test your code without spending credits, so you can keep building while you wait for an answer."* Directly addresses the two accidental-credit-spend incidents from Steps 5–6.

**Built:**
- `lib/fortyguardFixtures.ts` — `generateCachedHeatmapResult(aoiGeometry, granularity)` and `generateCachedSatelliteResult(lat, lon)`. Not static fixtures: the heatmap generator tiles the *actual input AOI's bbox* at the requested granularity (capped at 20×20 cells), assigns each cell a deterministic pseudo-random temperature in the 27–35°C range (spans all of `tempToColor`'s bands), and computes `stats_data` (`temperature_stats`, `temperature_frequency`, `normal_temperature_distribution`, `overall_temperature_distribution`) genuinely from the generated tiles — so the fixture is internally self-consistent, not just plausible-looking. Field names match the real captured shape from Step 5 exactly. Satellite fixture reuses the real class names observed in Step 4 (`Building`, `Road, Route`, `Sidewalk, Pavement`, `Tree`, `Earth, Ground`, `Grass`) with representative (not measured) percentages, and a verified-valid tiny placeholder PNG (checked its chunk structure — signature/IHDR/IDAT/IEND — with a Node script before using it) standing in for real imagery bytes cached mode doesn't have.
- `lib/fortyguard.ts`: `isCachedMode()` reads `FORTYGUARD_CACHED === "true"`; `runHeatmapGeneration`/`runSatelliteSegmentation` short-circuit to the fixture generators when on, and now both return `{ cached: boolean; result: T }` instead of bare `T` — callers must know whether a result is real. Overpass is untouched (already free/unlimited, no credit concept applies).
- Threaded `cached` through `app/api/heatmap/route.ts`, `app/api/landcover/route.ts`, and `store/analysisStore.ts`'s `EndpointResult<T>` type.
- `AnalyzePanel.tsx`: `SourceBadge` gained a `tone="cached"` amber variant; a new `DataSourceBadge` component swaps "Real (FortyGuard)" for "Cached (dev, no credit)" per-card based on the actual response's `cached` flag (not a static assumption) — Overpass's card badge stays hardcoded "Real (OpenStreetMap)" since it's never cached. Added explicit "Synthetic values for dev/testing — not a real measurement" captions on both cached cards, and skip rendering the (blank) placeholder images on the satellite card when cached, showing a text note instead.
- `.env.local`: added `FORTYGUARD_CACHED=true` — **cached mode is now the default.** Must be flipped to `false` (or the line removed) before the real demo/submission run.

**Validated live, end-to-end, for the first time without credit risk:** started the dev server, drew a real 2.03 km² AOI over downtown Phoenix, clicked "Analyze land cover" for real (safe now — cached mode on). All three cards loaded together and resolved together: Footprint cross-check showed real live Overpass data (18.9% buildings / 29.9% roads / 51.2% other, 1119 buildings + 2167 road segments — real, since Overpass isn't cached); Surface heatmap showed the amber "Cached (dev, no credit)" badge with self-consistent Min 27.0°C / Mean 31.1°C / Max 35.0°C from 360 generated tiles, rendered on the map as a full green→yellow→orange→red spread (confirming the noise function produces real variation, not a flat color); Satellite segmentation showed the same cached badge with the fixture's Building 27.4% / Road 21.8% / Tree 19.2% etc. This run also incidentally gave the first full live confirmation that Step 7's unified `analyzeAOI` (parallel fetch, single loading state, simultaneous card population) works correctly end-to-end in the browser, not just via injected test state. `tsc --noEmit` and `next lint` clean.

**Layout fix, 3 levels (`app/analyst/page.tsx` → `AnalystTabsShell.tsx` → `HotspotPanel.tsx`), plus the two map view components.** The report's suggested code assumed a different file layout (`app/analyst/components/AnalystLayout.tsx` etc.) that doesn't exist here — adapted the same `flex-col` + `h-full`/`flex-1 min-h-0` idiom onto the actual chain: `page.tsx`'s `main` (`flex flex-col overflow-hidden`, was `overflow-y-auto`) → a `min-h-0 flex-1 overflow-y-auto` wrapper around `SiteData`/`SavedSitesList` → `AnalystTabsShell`'s root (`h-full flex flex-col`) → its own `min-h-0 flex-1 overflow-y-auto` wrapper around `ContentArea` → `HotspotPanel` (`h-full flex flex-col`, tab row `shrink-0`, map area `min-h-0 flex-1`) → `HotspotGridView`/`HotspotSatelliteView` roots changed from a fixed `h-[440px]` to `h-full`.

Used `overflow-y-auto` at each `flex-1 min-h-0` boundary instead: inert (no visible scrollbar) for a tab that fills its space exactly like Hotspot's map, but still a safe local fallback — scoped to just that content region, not a page-level scrollbar — for a tab whose content is genuinely taller. **Two real bugs found only by measuring the live DOM (`getBoundingClientRect`/`clientHeight`/`scrollHeight` via `javascript_tool`), not by eyeballing screenshots — a screenshot at this viewport size looked correct even before either was fixed:**
1. `overflow-y-auto` alone leaves `overflow-x` at its default `visible` — but CSS's overflow computed-value rule silently promotes an unset axis to `auto` whenever the other axis is non-`visible`. `AnalystTabsShell`'s toolbar bar uses `-mx-6` to bleed edge-to-edge past `main`'s padding; with `overflow-x` implicitly `auto` on the two new `min-h-0 flex-1 overflow-y-auto` wrappers, that bleed was tripping a phantom *horizontal* scrollbar, and reserving space for it ate ~15px of *height* — enough to push the actual content into a real vertical overflow. Fixed by adding `overflow-x-hidden` alongside every `overflow-y-auto` in this chain (both wrapper divs).
2. The toolbar bar's `-mb-5` (paired with `main`'s `pb-5`) was a pre-existing trick that worked fine when `AnalystTabsShell` sat in unconstrained document flow, but inside a `h-full`-constrained flex-col parent, a negative bottom margin makes the *real rendered box* poke out past the parent's edge instead of actually reclaiming space — producing exactly the ~20px overflow this fix was meant to remove. Fixed by dropping `pb-5` from `main` and `-mb-5` from the toolbar bar entirely (they exactly canceled each other, so removing both nets zero visual change) — kept `-mx-6` since horizontal bleed is harmless once `overflow-x-hidden` is in place.

## Sub-task 3 — Shift Schedule (ISO 7243 / NIOSH REL)

**Resolved the flagged technical unknown before writing any code, per the brief's explicit instruction not to guess it.** ISO 7243/NIOSH REL heat-stress limits are published in WBGT, but FortyGuard only gives 2m air temperature — no humidity, wind, or radiant heat, and Operational Analyst can't call FortyGuard's `/v1/env_params` (which does have real heat index) since this page never calls FortyGuard at all (§5 intro). Researched (not guessed) two pieces via `WebSearch`/`WebFetch`, both now sourced in `lib/wbgt.ts`'s header comments:
- **WBGT approximation:** Australian Bureau of Meteorology's shade formula, `WBGT ≈ 0.567·T + 0.393·e + 3.94` (e = vapor pressure from an assumed relative humidity — no real humidity exists anywhere in a saved site record). Picked 40% RH as a disclosed middle-ground assumption (saved sites span both arid Phoenix and humid Houston in this project's own demo data).
- **NIOSH REL WBGT ceiling table** (NIOSH 2016 Criteria Document, via OSHA's Heat Hazard Recognition page): 4 workload levels (light/moderate/heavy/very heavy) × 2 acclimatization states (unacclimatized/acclimatized), in °C WBGT.

**Asked the user before picking defaults** (`AskUserQuestion`, not guessed, per the brief's explicit instruction): workload = **Moderate** (unacclimatized 25°C / acclimatized 28°C WBGT), acclimatization = **Unacclimatized** (the more protective assumption when a site's actual worker population is unknown) — also surfaced acclimatization as a second free parameter baked into the same table that the brief hadn't mentioned, rather than silently picking one.

**Classification design — 3 tiers, no invented margin:** Safe (WBGT ≤ 25°C, the unacclimatized limit — fine even for a non-heat-adapted worker), Caution (25–28°C — risky for unacclimatized workers, still within limit for acclimatized ones), Danger (>28°C — exceeds the limit regardless of acclimatization). Both boundaries are the table's own two published numbers for the chosen workload — no arbitrary offset invented for a 4th "Extreme Danger" tier the brief's example category list suggested, since that would need an unsourced number; flagged this tradeoff rather than quietly picking one.

**Built:**
- `lib/wbgt.ts` — `estimateWBGT(airTempC, rh?)`, `classifyShiftRisk(wbgtC, workload?)`, the sourced `NIOSH_REL_WBGT_C` table, and `SHIFT_SCHEDULE_ASSUMPTIONS_TEXT` (the full disclosure string, built from the same constants so the UI text and the actual thresholds can never drift apart).
